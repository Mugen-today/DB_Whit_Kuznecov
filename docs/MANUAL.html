GIS-MongoDB 0.11.2

Исправление импорта 0.11.1: Excel читает все листы, JSON имеет отдельную команду. По умолчанию — только проверка; запись требует --apply. Актуальные команды, Compass и диагностика. Прежние разделы и описания форматов ниже сохранены.

Новый автоматический импорт: py scripts/import_data.py "D:\Sources\file.xlsx". Поддерживаются XLSX, JSON, GeoJSON и GPKG распознаваемых структур; требуется только путь. Инструкция 0.11. Импорт независим от запуска; схема, роли, данные и volumes сохраняются. Историческая неполнота и неоднозначные ссылки явно отражаются в полном отчёте, без подстановки значений.

MongoDB хранит связанные документы, backend проверяет доступ, типы, связи и геометрию, QGIS показывает и редактирует все 17 пользовательских коллекций, Streamlit предоставляет dashboard. cases — дополнительная служебная коллекция.

Проект запускается с пустой БД. Исходных датасетов в поставке нет. Коллекции, индексы, роли и replica set создаются независимо от импорта. Excel и GeoPackage пользователь загружает отдельно, когда это требуется. Уже существующие документы и Docker volumes при обновлении сохраняются.

Первый запуск

Нужны Python 3.10+, Docker Engine/Desktop с Compose v2 и QGIS 3.28+ (проверен 3.40.6). Из корня проекта в PowerShell:

py scripts/manage.py doctor
py scripts/manage.py init
py scripts/manage.py volumes
py scripts/manage.py config --connections --local-api
py scripts/manage.py up --connections --local-api
py scripts/manage.py verify
py scripts/manage.py status

Linux/macOS: python3 вместо py. init нужен только для новой установки. Сохраните .env: там секреты и имена томов. Запуск не ищет A/B, manifest или папку data, не собирает и не запускает импортёр. QGIS — настольное приложение: установите dist/qgis_mongodb.zip через менеджер плагинов, перезапустите QGIS, подключитесь к 127.0.0.1:8000 с подходящим API-токеном из .env. Ожидаемая версия backend — 0.11.0. Пустые слои/таблицы — нормальное состояние.

Адрес Назначение
http://127.0.0.1:8000/health/ready Проверка технических подключений backend
http://127.0.0.1:8501 Dashboard; пустая база поддерживается всеми ролями

Необязательный импорт

GeoPackage: кнопка «Загрузить файл .gpkg в MongoDB» в плагине → выбрать файл и таблицу → сопоставить поля → выбрать строгий/частичный режим → проверить все строки → загрузить → сохранить полный CSV. Обработка геометрии/CRS остаётся в backend. Размер пакета не ограничивает число строк файла. Поддерживается 2D Point и непространственные таблицы, известная CRS преобразуется в EPSG:4326.

Excel, новые строгие записи: укажите путь к своему .xlsx. В выбранном листе первая строка содержит целевые имена вида Patient.passport, Patient.age, Patient.reg_date, Instances.date, Therapy.date_start, Therapy.diagnosis, Geodata.Longitude, Geodata.Latitude. Одна строка — связанный набор; диагноз можно записать JSON-массивом. Паспорт храните текстом, чтобы сохранить ведущие нули.

py scripts/import_excel.py "D:\Sources\records.xlsx" --sheet Cases
py scripts/import_excel.py "D:\Sources\records.xlsx" --sheet Cases --apply > import-report.jsonl

Без --apply выполняется полная проверка с проверкой внешних ключей, без записи документов. Для отдельных сущностей добавьте --mode entities; для частичного импорта ошибочного файла — --error-policy partial. Полный отчёт JSONL выводится в stdout; прогресс/ошибки команд Docker — в stderr. Служебный прогресс хранится в прежнем томе импорта. Повтор неизменённого файла не создаёт дубликатов.

Прежний Excel «лист — коллекция»: отдельный исторический административный путь:

py scripts/import_excel.py "D:\Sources\old.xlsx" --format collections --namespace test-dataset-a
py scripts/import_excel.py "D:\Sources\old.xlsx" --format collections --namespace test-dataset-a --historical --apply

Он сохраняет прежнее архивирование строк в cases, неполноту старых источников и insert-only ID; это не строгий ввод новых записей. Сначала изучите его отчёт. Для повторного импорта прежней базы сохраните прежний namespace; смена namespace создаёт другую идентичность. Не используйте этот режим для обхода новых правил. Исторический JSON-адаптер seed_b сохранён для явного административного вызова с внешним файлом; автоматической загрузки JSON при запуске больше нет.

Обновление существующей установки

Сохраните .env и все прежние volumes, замените файлы проекта, затем:

py scripts/manage.py configure
py scripts/manage.py config --connections --local-api
py scripts/manage.py up --connections --local-api
py scripts/manage.py verify
py scripts/manage.py status

Переустановите ZIP плагина и перезапустите QGIS. Не выполняйте повторный init или down -v. Источники A/B больше не нужны для запуска уже заполненной БД и не удаляются из MongoDB. Индексы дополняются без удаления существующих. Если датасеты были отслеживаемыми файлами вашего Git, уберите их из индекса по инструкции; исключение через .gitignore само по себе не удаляет уже отслеживаемые файлы и старые коммиты.

Правила и границы

  • Все 17 коллекций доступны QGIS с пагинацией без общего лимита. Права прежние: user читает/редактирует своё, guest не видит Social_group/Street/Building/Placement, reader анализирует всю базу и остаётся только для чтения.
  • Никаких фиктивных значений и скрытых пропусков. Критические ошибки останавливают оба режима импорта; необязательные поля дают предупреждение.
  • В строгом режиме ошибки полной предварительной проверки запрещают запись. При позднем сбое уже подтверждённые строки остаются; общей транзакции файла нет.
  • Кеш внешних ключей действует только внутри страницы проверки, ограничен памятью и не используется при записи: права и ссылки проверяются повторно.
  • Ответы выдаются страницами с байтовыми границами. QGIS хранит полный загруженный слой, а dashboard аналитика — всю выборку; память клиентов растёт с объёмом.

Исправление Version_20 / 0.11.1: автоматический Excel и JSON

Этот раздел задаёт актуальные команды; прежние разделы выше сохранены. import_excel.py обрабатывает все листы, --sheet Cases не нужен. import_json.py добавлен для testB_normalized_final.json. Обе команды используют общий import_launcher.py и backend auto_import.py. Без --apply выполняется только предварительная проверка, без записи MongoDB.

1. Подготовка и выбор файла

Откройте PowerShell в корне GIS-MongoDB, где находится docker-compose.yml. Сохраните прежний .env, STORAGE_DATA_VOLUME/STORAGE_CONFIG_VOLUME и том импорта. Для уже установленной базы не выполняйте init и down -v. Запустите сервисы:

py scripts/manage.py up --connections --local-api
py scripts/manage.py verify
py scripts/manage.py status

Для совершенно новой установки сначала выполните первоначальные шаги README. Импорт всегда отдельный и добровольный. Файлы находятся вне проекта; их не нужно копировать в data или Git. Укажите полный путь в кавычках, например: C:\Users\User\Downloads\Telegram Desktop\testB_normalized_final.json. Docker Desktop должен иметь доступ к выбранному файлу. Linux/macOS: python3 вместо py.

2. Excel: проверить все листы и затем записать

py scripts/import_excel.py "D:\Sources\test_datasetA.xlsx" --dry-run > import-excel-check.jsonl
py scripts/import_excel.py "D:\Sources\test_datasetA.xlsx" --apply > import-excel-apply.jsonl

Имя файла может быть test_datasetA_ispr_1.xlsx или другим: структура определяется по именам листов/полей. Первая строка каждого листа — заголовки. Имена известных коллекций сопоставляются с model.json, дополнительные исходные листы архивируются в cases с предупреждением, не удваивая нормализованных пациентов. Формат всех листов образца A не требует ни –sheet, ни –format, ни –historical.

3. JSON: проверить и записать

py scripts/import_json.py "D:\Sources\testB_normalized_final.json" --dry-run > import-json-check.jsonl
py scripts/import_json.py "D:\Sources\testB_normalized_final.json" --apply > import-json-apply.jsonl

Распознаются разделы Patient/Therapy/Instances/Location/Foci, Address_Refs и справочники образца B. Создаются только реально представленные сущности; не нужно искусственно наполнять все 17 коллекций, если части данных отсутствуют. Обе команды без указания режима эквивалентны –dry-run. Одновременные –dry-run и –apply отклоняются до запуска Docker.

После проверки откройте отчёт, изучите severity=critical/error и предупреждения, затем отдельно выполните ту же команду с –apply. Между вызовами применяются те же правила, но проверка выполняется заново, а не по устаревшему разрешению. Это исторический совместимый импорт: отсутствие паспортов/возраста и неоднозначные однозначные FK отражаются в отчёте; проверки интерактивного API остаются строгими. Смысл таких исключений подробно описан в docs/AUTO_IMPORT_0110.md.

4. ID, связи, геометрия и отчёт

MongoDB использует _id типа ObjectId. Корректные 24-символьные ID JSON преобразуются в BSON ObjectId без смены значения. Числовые ID Excel и их FK преобразуются согласованно прежним алгоритмом namespace test-dataset-a. id_instance/_id_instance корректно связываются с Instances.instance и Foci.id_instance. Geodata.geometry создаётся как Point в порядке долгота, широта. Даты, числа, bool и массивы приводятся по model.json.

–dry-run создаёт только локальный служебный план и отчёт: не вставляет документы, не обновляет существующие и не архивирует строки в cases. Итог status=dry-run, documents показывает планируемые количества, inserted пустой. –apply вставляет пакетами по 250, сохраняет прежние документы/правки и архивирует источник в cases. Повтор неизменённого файла с –apply не создаёт дубликатов; итог inserted равен 0. Совпадающие существующие ID не перезаписываются, даже если исходник изменился.

Отчёт JSONL: каждая строка — JSON-сообщение с stage, collection, row, field, reason, severity; последняя строка содержит summary. issues включает и warnings. Проверка исторического источника может закончиться с предупреждениями/ошибками отдельных полей: они не становятся фиктивными значениями. Исходные значения при –apply сохраняются в cases. Конфликт ID/неисправимая геометрия/повреждение файла останавливают процесс. Код завершения доступен в PowerShell как $LASTEXITCODE. Общего отката файла при позднем сбое записи нет; повтор дозаполняет отсутствующие ID.

5. Проверка в MongoDB Compass

Подключитесь с существующей строкой подключения и учётной записью с нужными правами. Если локальный порт MongoDB не опубликован, используйте штатный локальный overlay, описанный в разделе подключения; порт backend 8000 не является портом MongoDB. Откройте Schema, нажмите Refresh и проверьте коллекции Patient, Instances, Therapy, Geodata, Location, Foci и cases. Не удаляйте базу перед проверкой повторного импорта.

В Compass встроенном mongosh выполните:

use Schema
db.Patient.countDocuments({})
db.Instances.countDocuments({})
db.Geodata.countDocuments({})
db.Geodata.countDocuments({"geometry.type":"Point","geometry.coordinates.1":{$exists:true}})
db.Geodata.findOne({}, {_id:1, Longitude:1, Latitude:1, geometry:1})
db.Instances.findOne({}, {_id:1, instance:1, patient:1, therapy:1, date:1})

Вкладка Documents принимает только фильтры, не команду db.collection.find(). Там можно проверить отсутствующую геометрию фильтром:

{"$or":[{"geometry":{"$exists":false}},{"geometry":null}]}

Для основной связи во вкладке Aggregations коллекции Foci используйте pipeline:

[
 {"$match":{"id_instance":{"$exists":true}}},
 {"$lookup":{"from":"Instances","localField":"id_instance","foreignField":"instance","as":"target"}},
 {"$match":{"target":{"$size":0}}},
 {"$limit":10}
]

Пустой результат означает отсутствие висячих проверяемых ссылок, но отдельно проверьте отчёт на ссылки, которые не удалось перенести. Аналогично сопоставьте Therapy.patient с Patient._id и Location.address.geodata с Geodata._id. Сверяйте прирост с inserted из отчёта, а не с числом всех листовых строк Excel. При базе без прежних данных оба предоставленных образца в тесте дали суммарно 41938 Patient/Instances и 18509 Geodata. В рабочей базе количества могут отличаться; при –dry-run они должны оставаться неизменными.

Для старого строгого плоского Excel с заголовками Collection.field используйте scripts/import_excel_records.py FILE --sheet Cases [--apply] — это отдельный сохранённый инструмент, а не обязательная настройка импорта test_datasetA.xlsx.

Перед обновлением сохраните .env и резервную копию БД. Замените исходники, пересоберите backend штатным up, переустановите ZIP плагина (версия 0.11.1). Version_21 / 0.11.2: временное хранилище и блокировки GPKG

Распознаваемые структуры

  • XLSX образца A: имя листа — коллекция, первая строка — поля. Дополнительные исходные листы архивируются в cases и явно отмечаются как не нормализованные.
  • JSON образца final B: массив объектов с разделами Patient, Therapy, Instances, Location, Foci, Address_Refs и справочниками. JSON-массив читается постепенно.
  • GeoJSON FeatureCollection: properties содержит такие же разделы либо поля Collection.field; geometry должна быть 2D Point EPSG:4326. FeatureCollection сейчас загружается в память целиком — ограничения числа записей нет, но нужен RAM.
  • GPKG: таблицы с именами коллекций/полями модели либо таблица связанных записей с полями Collection.field. Также распознаются однозначные имена passport, age, diagnosis, Longitude/Latitude; registered/started/event_date соответствуют Patient.reg_date/Therapy.date_start/Instances.date. Геометрию Point и CRS преобразует существующий backend-адаптер. Неизвестная CRS останавливает импорт.

Произвольные имена вроде name/type без контекста коллекции не угадываются. Нераспознанные данные архивируются в cases с предупреждением, а не исчезают. GeoJSON/GPKG не проверялись на реальных образцах пользователя: такие образцы не предоставлены; проверены генерируемые тестовые структуры выше.

ID, типы и связи

Используется MongoDB _id типа ObjectId; дублирующее поле id не добавляется. Корректные 24-символьные исходные ID сохраняются с преобразованием BSON-типа. Числовые/другие ключи Excel нормализуются прежним алгоритмом namespace test-dataset-a, чтобы ссылки совпадали с предыдущим импортом. Для остальных сгенерированных ключей используется SHA256 источника, коллекция и позиция строки. Повтор неизменённого файла сохраняет те же ID. Изменённый источник без явных ID может создать другие документы — это не поиск одинаковых людей по атрибутам.

Исправляются Bouilding/Setlement/Settelment, courpus, treatment_procedure, _id_instance/id_instance и Foci.instances. Ссылки приводятся к направлениям model.json; Location.address.geodata связывается с Geodata, Foci.location — с Location, Foci.id_instance — с Instances.instance. Геометрия сохраняется как GeoJSON Point, Longitude/Latitude согласованы. ISO-даты становятся BSON Date, числовые/логические поля и массивы преобразуются по модели.

Историческая неполнота и ограничения модели

Это административный исторический импорт с техническими полномочиями хоста, а не ослабление API создания новых записей. В предоставленных образцах есть NULL passport/age и неоднозначные справочники. Отсутствующие значения не выдумываются: документ сохраняет допустимую моделью хранения неполноту, предупреждение попадает в отчёт. Строгие правила интерактивного API не изменены.

Неизвестные поля и исходные ошибочные значения сохраняются в cases. Значение, которое нельзя привести к типу модели, исключается из нормализованного документа с явной ошибкой поля в отчёте. Неразрешённая ссылка исключается с ошибкой; фиктивная целевая сущность не создаётся. Исходная ссылка остаётся в cases.

В B один ID улицы может ссылаться на несколько зданий, а модель допускает только одну ссылку Street.building. Аналогичные конфликты бывают в других справочниках. Такую ссылку нельзя переносить выбором «последнего» значения: она исключается, помечается внутренним _ambiguous_links, все исходные связи архивируются. Полностью выразить такую связь без изменения модели на один-ко-многим невозможно. Конфликт остальных атрибутов одного ID — критическая ошибка до начала записи.

Запись и отчёт

Вся адаптация и проверка выполняются в служебном SQLite до записи. Затем документы вставляются пакетами по 250, существующие ID не обновляются. Поэтому сохраняются прежние пользовательские правки. В конце cases получает архив исходных строк. Если запись прервана, ранее подтверждённые пакеты остаются; повтор той же команды дозаполняет отсутствующие ID без дубликатов. Общей транзакции файла нет. Внешние ссылки проверяются перед записью, но конкурентное удаление документов внешними инструментами после проверки этим историческим путём не блокируется.

Отчёт содержит stage, collection, row, field, reason, severity; последняя строка содержит summary: SHA256, исходные строки, число нормализованных документов, вставленные документы и количество сообщений. Счётчик issues включает предупреждения, а не только ошибки. Все сообщения выводятся без ограничения preview в 100 строк. При критическом сбое процесс возвращает ненулевой код. Для прямого Python-вызова доступно python -m app.modules.auto_import FILE --report REPORT.jsonl из backend с настроенным окружением MongoDB. Не направляйте stdout в сам исходный файл.

Датасеты/отчёты могут содержать персональные данные; храните их вне Git. Существующие .env, MongoDB volumes и том импорта при обновлении сохраняются. Обновите backend и ZIP плагина вместе; ожидаемая версия сессии 0.11.0. Предыдущие руководства 0.10 описывают прежние команды и оптимизацию; эта инструкция задаёт новый консольный путь.

1. Назначение и основной принцип

Проект связывает нормализованные документы MongoDB с настольной ГИС и dashboard. Пользователь формулирует действие в QGIS либо браузере. Backend определяет проверенную сервером роль, проверяет атрибуты и ссылки, выполняет чтение/запись в MongoDB и возвращает данные в пригодном для клиента виде. Клиент не получает пароли технических пользователей БД и не меняет model.json.

В раннем описании использовались отдельные download/upload. В текущей поставке эти функции объединены в backend/app/modules. Обслуживание ведётся для storage, backend, dashboard и одноразового excel-import. QGIS устанавливается на компьютер пользователя; это не контейнер. В схемах стрелки API означают запрос и ответ, а не копирование всей БД при каждом действии.

3. Схема и связи

model.json — единственный канонический файл BSON-схем. Названия: Instances, Region, Municipality, Settlement, Street, Building, Placement, Reception, Geodata, Patient, Gender, Social_group, Therapy, Severity, Influence, Foci, Location. cases — отдельный служебный архив, поэтому физически после инициализации можно видеть 18 коллекций.

Стрелка указывает от поля-ссылки к целевому документу. Не переосмысливайте адресные ссылки как обратные: именно Region.municipality → Municipality._id, затем Municipality.settlement → Settlement._id и далее по схеме. Критическая особенность: Foci.id_instance ссылается на Instances.instance, а не просто на _id по догадке. Location.address.geodata указывает на Geodata; Patient сам по себе не содержит точку.

Новые _id и связанные значения генерируются backend. _owner_id ограничивает пользовательские документы; qgis_revision позволяет обнаружить конкурентную правку. _request_hash обеспечивает проверку повторного запроса. Эти метаданные не являются полями, которые пользователь должен сопоставлять с GPKG.

Историческая схема допускает неполноту исходных данных. Поэтому обязательность нового пользовательского ввода задаётся одновременно model.json и бизнес-правилами records/entities. В GPKG список требований приходит из backend; нельзя считать, что required только с _id означает возможность создать пустого нового пациента.

4. Развёртывание и обновление

4.1. Новая учебная установка

Рабочая папка должна содержать docker-compose.yml, backend, storage, dashboard, и scripts. Запустите Docker. В корне выполните doctor, затем init, volumes, config –connections –local-api, up –connections –local-api, verify и status. Точные команды приведены в README и практикуме. При первом запуске нужны сеть для получения образов/зависимостей, свободный диск под MongoDB. Исходные файлы для запуска не нужны.

init выполняют один раз: существующий .env он не перезаписывает. volumes — явная подготовка новой установки. Compose использует external:false и способен создать отсутствующий именованный том; при обновлении это не доказывает, что подключён нужный прежний том. Всегда сверяйте имена до запуска.

4.2. Что делает up

  1. Проверяет, не используются ли тома старым работающим MongoDB-сервисом.
  2. Останавливает backend на время подготовки хранилища.
  3. Запускает storage и ждёт контейнерной готовности.
  4. provision настраивает replica set, схему, роли, индексы и подготовку геометрии.
  5. verify проверяет фактическую схему, права и служебные подключения.
  6. С –connections собирает backend/dashboard и ждёт их готовности. Импортёр не запускается.

Геометрия проверяется один раз внутри provision; повторный проход после seed удалён вместе с автоматическим seed.

Контейнер storage Healthy означает доступность окончательного mongod и ping. Это отличается от корректности всех ролей/валидаторов и от заполнения источников. Для прикладной проверки нужен verify; нулевое количество документов допустимо. Backend /health/ready отдельно проверяет свои технические подключения; /health/live сообщает только о живом процессе.

4.3. Обновление

Остановите пользовательские изменения и сделайте копию. Сохраните прежний .env, точные имена data/config-томов и нужный кеш незавершённого импорта. Разверните новые файлы поверх версии проекта, верните .env, выполните configure → config → up → verify. Перезапустите QGIS после переустановки ZIP. Сравните backend_version с 0.10.0. Не заменяйте .env шаблоном и не используйте init для ремонта старых паролей.

Обычный up — полноценный запуск с подготовкой схемы и сборкой, а не только лёгкий restart. Он может занять время. Миграцию старых опечаток выполняют отдельно через migrate-plan и migrate; эти команды останавливают backend и автоматически не возвращают весь интерфейс в работу — после них нужен обычный up.

5. Пустая установка и необязательные источники

После новой установки все 17 пользовательских коллекций и cases пусты, роли и индексы готовы. В dashboard показываются нули и отсутствие данных, QGIS создаёт пустые слои/таблицы со схемой. Наличие источников не является условием readiness. В существующей установке сохраняются прежние документы и маркеры cases.

Пользователь сам выбирает внешний GPKG в плагине или задаёт путь XLSX командой py scripts/import_excel.py "D:\Sources\records.xlsx". Данные не копируются в репозиторий; Excel монтируется в одноразовый контейнер read-only. Подробнее о строгом формате строк и прежнем формате листов: OPTIONAL_IMPORT_0100.md.

geospatial-index.js выполняется независимо от импорта. Поэтому восстановление пустой geometry не требует удалять источник или запускать init. Валидная новая geometry — {type:"Point",coordinates:[Longitude,Latitude]}; порядок всегда долгота, широта. Отсутствующая/null/пустая geometry восстанавливается только при корректных координатах. Прежнее пустое значение сохраняется в _previous_geometry; непустая ошибочная геометрия не переписывается молча. Частичный индекс gis_valid_geometry включает только помеченные валидные точки.

6. Доступ и секреты

В QGIS имя само по себе не предоставляет права. Backend сопоставляет Bearer-токен и при наличии X-GIS-User проверяет имя. Переключение профиля сбрасывает прежние управляемые слои/каталог и повторно получает права. Несохранённый локальный буфер нельзя терять незаметно: пользователь решает, сохранить его или отменить.

7. Выгрузка и редактирование QGIS

Клиент запрашивает каталог доступных коллекций, затем страницы /v1/collections. Курсор основан на _id; _key представляет идентификаторы разных BSON-типов без неоднозначного преобразования. Размер ответа — не предел коллекции: загрузчик проходит все next. Decimal128/Binary и сложные значения передаются в совместимом JSON/Extended JSON; служебные поля скрываются.

Geodata становится Point EPSG:4326; остальные коллекции становятся таблицами без геометрии. Даже пустая таблица имеет поля схемы. Клиент хранит локальный memory cache. После открытия сохранённого QGIS-проекта данные нужно получить заново: проект не превращает этот кеш в постоянный MongoDB provider.

При сохранении backend проверяет роль, владельца, типы, обязательность изменяемых полей, FK и ревизию. Успех возвращает новую ревизию и согласованные координаты/ geometry; отказ сохраняет буфер для исправления. Пакет до 200 правок атомарен; несколько пакетов одного слоя — не одна общая транзакция. При частично выполненных пакетах сначала выясните подтверждённое состояние, не предполагая откат всего слоя. Создание/удаление строк непосредственно memory provider отключено: создавайте через форму либо импорт; пользовательское удаление документов не предоставлено.

Экспорт в GPKG выполняется штатным «Сохранить объекты как…» QGIS для каждой таблицы/слоя. Пространственная геометрия слоя и строковый атрибут geometry — разные сущности. При повторном импорте выбирайте реальный Point-столбец GPKG через флажок, а не пытайтесь сопоставить текстовый JSON в geometry вместо геометрии таблицы.

8. Новый связанный набор и GPKG

Полный набор требует все четыре группы: местоположение, Instances.date, Patient.passport/age/reg_date, Therapy.date_start/diagnosis. Местоположение — Longitude и Latitude вместе либо все описательные поля пяти адресных коллекций. Location/Foci и ссылки создаёт backend. Полная адресная ветка может не создать точку, если координаты не переданы: наличие адреса не означает выполненное геокодирование.

Для частичного GPKG обязательны поля выбранных сущностей, а не все атрибуты всех 17 коллекций. Therapy требует существующий доступный patient либо Patient той же строки; Geodata может быть единственной сущностью при наличии Point. Для Region/ Municipality/Settlement/Street нужен name, для Building — house; точные требования и типы приходят backend. Генерируемые _id/instance и метаданные не сопоставляются.

Передача идёт блоками ≤4 МиБ в отдельный дисковый том. Проверяются завершённость, SHA256 и структура SQLite. После сопоставления создаётся дисковое задание. Страницы читаются по PK, проверяются и складываются в служебный SQLite. До проверки последней строки ни одна строка задания не импортируется в MongoDB. Ошибки показываются с номерами; ответ ограничивает предварительный просмотр 100 ошибками, а полный отчёт доступен в CSV без этого ограничения. В строгом режиме любая ошибка строки запрещает запись задания; в частичном ошибочные строки явно отклоняются. Критические ошибки останавливают оба режима. Затем пользователь отдельно подтверждает запись кнопкой. Общего отката уже подтверждённых строк нет.

Импорт применяет до 25 строк за шаг, сохраняет позицию после каждой подтверждённой строки. При сбое задания пользователь нажимает продолжение. После перезапуска backend позиция берётся с диска, а не из догадки клиента. Повтор после потерянного подтверждения использует те же ID. Это защита повторной доставки, а не поиск одинаковых пациентов по ФИО/паспорту или одинаковых точек по координатам.

График — расчёт счётчика при пакетах по 25, не замер производительности. 5003 строки могут потребовать 201 пакет. В действительности байтовая граница иногда уменьшает пакет; сервер всегда сообщает реальную подтверждённую позицию.

Сессии привязаны к владельцу/роли. Не меняйте исходный файл во время передачи и сопоставление после частичного импорта. Неактивный служебный кеш истекает через 7 дней; он очищается при начале последующих загрузок. Рабочие документы MongoDB при этой очистке не удаляются. До завершения задания нужен диск и для GPKG, и для подготовленных строк; это не только размер исходного файла.

11. Резервирование и восстановление

Каталог storage/backup — место для файлов, не планировщик резервного копирования. Для рабочей установки администратор задаёт периодичность и срок хранения. Копия должна включать БД, защищённый .env, конфигурацию установки и при необходимости кеш активного импорта. Логический dump MongoDB не содержит служебные SQLite-задания. Не копируйте файлы живого WiredTiger обычным файловым копированием.

Ниже — пример ручной логической копии при остановленных прикладных записях; он не выполнялся в среде подготовки, поскольку Docker daemon недоступен. Убедитесь, что в образе есть mongodump и достаточно места в /tmp контейнера. При больших базах администратор выбирает отдельное хранилище копий.

На хосте из корня проекта:

docker compose --profile connections stop backend dashboard
docker compose exec storage bash

Внутри Bash контейнера (это уже не PowerShell):

command -v mongodump
umask 077
mongodump --host 127.0.0.1 --port 27017 \
  --username "$MONGO_INITDB_ROOT_USERNAME" \
  --password "$MONGO_INITDB_ROOT_PASSWORD" \
  --authenticationDatabase admin --oplog \
  --archive=/tmp/gis-backup.archive.gz --gzip
exit

На хосте:

$backupFile = ".\storage\backup\gis-" + (Get-Date -Format "yyyyMMdd-HHmmss") + ".archive.gz"
docker compose cp storage:/tmp/gis-backup.archive.gz $backupFile
Get-FileHash -Path $backupFile -Algorithm SHA256
py scripts/manage.py up --connections --local-api

В этой форме –oplog требует полной копии: не добавляйте –db Schema к данному примеру. Файл содержит административные данные и нуждается в защищённом хранении. Не перезаписывайте единственную предыдущую пригодную копию одним и тем же именем; назначьте имя по дате/установке. Не помещайте её в публичный Git.

Восстановление сначала проверяют на отдельной установке с отдельными томами. Администратор подготавливает её аутентификацию и копирует архив. Базовая команда внутри целевого контейнера — mongorestore с –archive, –gzip и –oplogReplay, аутентификацией к целевой admin. Не используйте –drop против рабочей БД. После восстановления необходимо проверить учётные данные из копии, Schema, количества, связи, геометрию и фактическую готовность сервисов. Полный dump может восстановить прежние пользователи/роли: новый .env не становится автоматически совместим с их паролями. Только успешно проверенное восстановление подтверждает пригодность копии. Данный проект не содержит команды manage.py restore.

Официальные параметры инструментов: mongodump и mongorestore.

4. Определите режим: впервые или обновление

4.1. Если это новая отдельная учебная установка

py scripts/manage.py init

Создаётся приватный .env с уникальными секретами и именами томов. Скрипт не должен перезаписывать существующий .env. Сообщение о существующем файле — повод проверить режим работы, а не удалить файл. Откройте .env локально и найдите имена STORAGE_DATA_VOLUME/STORAGE_CONFIG_VOLUME; сохраните их в закрытой записи вместе с резервной копией .env. Не вставляйте содержимое .env в отчёт.

Далее:

py scripts/manage.py volumes
py scripts/manage.py config --connections --local-api

volumes создаёт отсутствующие data/config-тома указанной установки либо сообщает, что использует существующие. config проверяет объединённую конфигурацию Compose; он не доказывает, что сервер запущен или данные загружены. Ключ –local-api применяют вместе с –connections. Для новой установки выполняйте шаги в этом порядке, чтобы видеть, с какими томами работает проект.

4.2. Если у вас уже есть БД

Не выполняйте init. Сохраните старый .env и резервную копию данных. Замените файлы поставки, оставив прежний .env в корне, затем:

py scripts/manage.py configure
py scripts/manage.py config --connections --local-api

configure добавляет отсутствующие новые секреты, не меняя существующие. Он не исправляет уже имеющийся неправильный пароль и не объединяет две разные БД. До up сверяйте прежние имена томов. Не используйте новые случайные имена как «ремонт»: это может скрыть старую БД за пустой установкой.

10. Выгрузите все коллекции

Отметьте «Выбрать все» либо нужные флажки. Нажмите «Загрузить выбранные коллекции полностью». Дождитесь завершения, проверьте число ошибок. Во время загрузки клиент читает страницы, а не останавливается на первой странице.

В панели слоёв Geodata имеет геометрию Point EPSG:4326. Patient и другие коллекции представлены обычными таблицами без геометрии — это правильное поведение. Откройте таблицу атрибутов каждого контрольного слоя и сравните количества с MongoDB через countDocuments. Пустая коллекция должна добавляться как пустая таблица.

Служебный _key нужен для адресации документа с любым поддерживаемым типом _id. Не редактируйте _id, _key, instance, qgis_revision. Вложенные структуры/массивы часто видны строкой JSON: это транспортное представление, а не изменение исходного BSON-типа в MongoDB.

11. Проверьте Geodata отдельно

В консоли плагина выполните по очереди:

db.Geodata.countDocuments({})
db.Geodata.countDocuments({"geometry.type":"Point", "geometry.coordinates.1":{$exists:true}})
db.Geodata.find({$or:[{geometry:{$exists:false}},{geometry:null},{geometry:{}}]}).limit(10)

В новой пустой базе первые два значения — 0, третий запрос возвращает пустой результат. После пространственного импорта сравните число точек и число валидных geometry; абсолютное количество определяется выбранным источником.

Проверьте у нескольких объектов четыре вещи: атрибут Longitude, атрибут Latitude, сохранённый JSON geometry и реальную геометрию слоя QGIS. Пример точки:

{"type":"Point","coordinates":[30.3,59.9]}

30.3 — долгота, 59.9 — широта. Не меняйте порядок по привычке из записи «широта, долгота». Надпись CRS проекта в правом нижнем углу QGIS не доказывает, что исходный файл имеет эту CRS.

Если поле geometry старых записей пусто, в терминале хоста:

py scripts/manage.py geometry

Затем заново загрузите Geodata в плагине. Эта команда использует реальные координаты и сохраняет прежнее пустое значение. При неверных/отсутствующих координатах она не создаёт вымышленную точку. Не заполняйте всем объектам [0,0] ради исчезновения предупреждения. Внешне отрисованная backend точка и наличие сохранённого поля в MongoDB — разные проверки, поэтому проверяются обе.

12. Выполните пользовательские запросы

Откройте «Консоль MongoDB». Вставьте запрос в редактор и нажмите выполнение. Редактор отправляет введённый текст, а не всегда стандартный пример.

Задача Запрос
Несколько пациентов db.Patient.find({}).limit(5)
Фильтр и сортировка db.Patient.find({age:{$gte:40}}).sort({age:-1}).limit(20)
Подсчёт без ограничения первой страницей db["Patient"].countDocuments({age:{$gte:40}})
Разные возраста db.getCollection("Patient").distinct("age")
Агрегация db.Instances.aggregate([{$group:{_id:"$patient",n:{$sum:1}}},{$sort:{n:-1}}])
Regex db.Geodata.find({"geometry.type":/^Point$/i}).limit(5)

Пространственный пример, расстояние задаётся в метрах для этого GeoJSON-запроса:

db.Geodata.find({geometry:{$near:{$geometry:{type:"Point",coordinates:[30,60]},$maxDistance:10000}}}).limit(10)

Для поля _id типа ObjectId используйте ObjectId("24-символьное-hex-значение") с настоящим идентификатором документа. Простая строка с теми же символами — другой BSON-тип и может не найти документ. Не копируйте текст заполнителя как ID.

Если результатов больше страницы, нажимайте «Следующая страница результата». pretty() и toArray() поддерживаются как оформление, но не заставляют сервер выдать всю БД одним ответом. Курсор консоли истекает после 15 минут без продолжения. Для повторного полного запроса выполните его заново.

Ошибочный запрос должен показывать ошибку, не создавать пустой «успешный» результат. Не используйте import os, print произвольного Python, out/merge или попытки изменить роль в теле запроса. Для проверки прав подключитесь guest и запросите Social_group: ожидается отказ, а не пустая таблица, выдаваемая за отсутствие данных.

13. Создайте учебный связанный набор

Проводите упражнение только в учебной БД. Для новой клинической записи нажмите «Новая запись»; откроется форма «Новый связанный набор» с request_id. Сохраните автоматически созданный request_id и заполните entities. Пример entities:

{
  "Geodata":{"Longitude":30.3,"Latitude":59.9},
  "Instances":{"date":"2026-11-11"},
  "Patient":{"passport":"TRAINING-001","age":25,"reg_date":"2026-11-11"},
  "Therapy":{"date_start":"2026-11-11","diagnosis":["TRAINING"]}
}

Это условные значения для обучения, не клиническая запись реального пациента. Вставьте этот объект вместо entities внутри полного шаблона; не удаляйте request_id. diagnosis — массив, age — число без кавычек, даты — ISO-строки, passport — строка для сохранения ведущих нулей. Нажмите проверку/отправку.

Должны создаться также Location и Foci; Patient–Therapy–Instances и местоположение связываются автоматически. Найдите Patient по TRAINING-001, запишите его _id в закрытом учебном протоколе и проверьте ссылки через чтение. Не вводите ID руками в форме полного набора. Удалите одно обязательное поле и убедитесь, что запрос отклоняется, а не создаёт неполный новый случай. Для нового отличающегося набора нужен новый request_id; повтор прежнего с другим содержимым вызывает конфликт.

Адресная альтернатива требует все пять групп: Region, Municipality, Settlement, Street, Building. В полном режиме нужны все описательные поля этой цепочки: Region.name, Municipality.name, Settlement.name/type, Street.name, Building.house/corpus/edificate/fraction/letters. Числовые поля Building остаются целочисленными по model.json; не подменяйте отсутствующее значение выдуманным нулём. Наличие адреса без координат не даёт точку на карте: геокодирование не реализовано.

14. Подготовьте собственный GPKG

Нужен завершённый файл GeoPackage со стабильным первичным ключом таблицы, например fid. Выбранная геометрия должна быть 2D Point, а CRS — реально определённой. Polygon, LineString, MultiPoint и произвольные 3D-геометрии текущий импорт не поддерживает. Если в файле несколько таблиц, импортируется выбранная, затем можно обработать другую.

В QGIS заранее откройте исходную таблицу и проверьте число строк, тип геометрии, CRS и отсутствие NULL в обязательных полях. Завершите редактирование файла перед передачей. Переименование CRS не заменяет корректное преобразование координат. Для непространственной таблицы достаточно атрибутов; флажок геометрии в диалоге будет недоступен. Не добавляйте ненужные фиктивные координаты.

14.1. Минимальные варианты сопоставления

Что создаём Сопоставляем Что не требуется

Только Patient passport, age, reg_date Геометрия и остальные коллекции

15. Выполните пакетный импорт GPKG

  1. В плагине нажмите «Загрузить файл .gpkg в MongoDB».
  2. Выберите файл. Плагин передаёт блоки до 4 МиБ, а backend сохраняет их на диск. Не закрывайте/не изменяйте исходный файл в процессе передачи.
  3. После передачи дождитесь списка таблиц. Выберите нужную и проверьте показанное число строк.
  4. Выберите «Отдельные коллекции — частичное сопоставление» либо полный режим.
  5. Сопоставьте реальные исходные столбцы с целевыми полями. Оставьте ненужные назначения в состоянии «не сопоставлено». PK и служебные поля генерирует backend.
  6. Если нужна Point-геометрия таблицы, оставьте флажок. Не путайте её с текстовым атрибутом geometry, который мог появиться при экспорте JSON из MongoDB.
  7. После паузы ввода примерно 0,7 секунды начинается проверка. Можно нажать «Проверить все строки сейчас». Смена назначения сбрасывает предыдущее подтверждение.
  8. Дождитесь конца всех страниц. Обязательные поля, типы, доступность FK и CRS проверяются сервером. Ошибка последней строки тоже запрещает начало записи.
  9. После успеха нажмите «Загрузить в MongoDB». Наблюдайте «загружено X из N».
  10. Завершение — X=N и сообщение об окончании. Проверьте MongoDB и перечитайте затронутые коллекции в QGIS.

Необязательные значения NULL/пустая строка пропускаются. Обязательное поле от этого не становится необязательным. Если все сопоставленные обязательные атрибуты выбранного Patient пусты, строка отвергается; backend не должен молча импортировать только её точку.

4 МиБ, 250 проверяемых строк, 25 записываемых строк — размеры шагов. Это не общий предел файла. В тесте 5003 строки прошли из файла 43589632 байта. Размеры отдельных ячеек/строк и тип геометрии всё равно ограничены; без свободного диска продолжение невозможно. Неисправность «1..1000 rows» означает старую версию backend или плагина.

16. Продолжите прерванный импорт

Если окно закрыто или связь пропала, не создавайте сразу новый отличающийся файл. Вновь откройте диалог под тем же подключением/владельцем и нажмите «Продолжить после прерывания». Плагин восстановит сохранённое задание. Сервер определит, сколько строк действительно подтверждено; число последней надписи на экране может отставать от последнего завершившегося запроса.

При paused прочитайте номер и причину: например, FK перестал быть доступным после проверки. Исправьте причину и продолжите тот же job. Подтверждённые строки не откатываются, непрошедшая строка не пропускается. Повтор завершённого задания не добавляет те же документы заново.

Это не дедупликация любых похожих файлов. Новый файл с другим содержимым или другими PK может породить новые документы. Не меняйте сопоставление во время частичного импорта ради «дозагрузки»: прежние ID с другим содержимым дадут конфликт. Через 7 дней неактивности служебная сессия истекает; выберите файл заново, сохраняя понимание уже записанных документов. В отчёт можно записывать job_id, но не токены.

17. Отредактируйте данные и проверьте синхронизацию

Выберите свой учебный Patient и включите обычное редактирование таблицы QGIS. Измените age, сохраните. Выполните find по _id или тренировочному passport и проверьте значение в MongoDB. При необходимости загрузите слой заново и сравните. Затем отдельно проверьте изменение Longitude: backend должен согласовать geometry.

Вложенные объекты и массивы удобнее изменять JSON-формой «Изменить выбранную». Выберите ровно одну запись. Не удаляйте служебные идентификаторы и не меняйте qgis_revision. Не открывайте одновременно независимые правки одного документа, не понимая конфликтов: старый номер ревизии приводит к 409 и требует сверки.

Для учебной проверки откажитесь от некорректного возраста 140: сервер должен отклонить сохранение, а буфер остаться редактируемым. Исправьте значение, затем повторите сохранение. У аналитика/гостя слой должен быть только на чтение. Карандаш QGIS не должен служить способом обойти роль.

Обычное добавление/удаление строк memory provider не предусмотрено. Не путайте удаление слоя из проекта с удалением документа MongoDB: первое убирает локальное представление, второе API вообще не предоставляет.

18. Экспортируйте пространственные и непространственные данные

В панели QGIS выберите слой/таблицу → экспорт → «Сохранить объекты как…» → GeoPackage. Назначьте файл и уникальное имя таблицы. Для ручной read-only проверки подключения в PowerShell можно временно прочитать только нужный токен из собственного .env, не печатая его:

$token = (Get-Content .env | Where-Object { $_ -like 'QGIS_USER_TOKEN=*' }) -replace '^QGIS_USER_TOKEN=', ''
$headers = @{ Authorization = "Bearer $token"; 'X-GIS-User' = 'qgis-user' }
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/v1/session' -Headers $headers
Remove-Variable token, headers

Пример рассчитан на стандартный .env, созданный init, с незаключённым в кавычки значением QGIS_USER_TOKEN. Не подставляйте здесь пароль root. Отправлять токены в URL или демонстрировать строку $token преподавателю не требуется.

Практикум дополнения 0.9.0: два режима и полный отчёт

Выполняйте на отдельной учебной установке. Подготовьте Point-GPKG с тремя строками, полями passport, age, registered и известной CRS. У одной строки оставьте age NULL. Сохраните копию исходного файла; не исправляйте его во время задания.

  1. Подключитесь в QGIS с правами записи. Выберите файл и сопоставьте Patient.passport, Patient.age, Patient.reg_date; включите геометрию. Не сопоставляйте необязательные поля.
  2. Оставьте строгий режим и дождитесь проверки всех трёх строк. Кнопка записи должна остаться недоступной; MongoDB не должна получить документы этого задания.
  3. Сохраните CSV. Найдите ошибку Patient.age, номер исходной строки и validation; отсутствие необязательных полей должно быть warning, а не ошибкой записи.
  4. Переключитесь на частичный режим и дождитесь новой полной проверки. Должно быть две корректные строки и одна отклонённая. Сводка покажет 2 успешные строки и 4 подтверждённых документа.
  5. Сохраните полный CSV. Повторите тот же неизменённый файл: новых документов быть не должно, подтверждённые будут отмечены повторно использованными.

  7. Для проверки продолжения на учебной установке прервите backend после нескольких подтверждённых строк, восстановите его с тем же томом импорта и нажмите продолжение. Сверьте счётчики и отсутствие дубликатов. Строки до сбоя сохраняются; автоматического отката всего файла нет. Не удаляйте тома ради этого упражнения.

Version_21 / 0.11.2 — хранилище и устойчивость импорта

Основа: последняя доступная поставка этого чата 0.11.1. Отдельный архив локальной Version_21 не предоставлялся. Рабочие данные и Docker volumes не подключались.

Исправления

  • Временная SQLite-база и полный отчёт перенесены из /tmp в существующий дисковый GPKG_UPLOAD_DIR (/var/lib/gis-imports). У импортёра /tmp ограничен tmpfs 256 МиБ; разжатый Excel, архив строк, журнал и отчёт могли превысить этот предел.
  • Исходные строки промежуточного SQLite сжимаются zlib без потерь. При записи cases восстанавливается прежний BSON: менять клиентов/схему не требуется.
  • Кеш staging SQLite ограничен 2 МиБ, это не предел всего процесса Python. В summary добавлен staging_bytes — размер основного файла после подготовки.
  • ExitStack/closing закрывают соединение даже при сбое создания таблиц/индексов; source iterator и последний курсор закрываются до очистки временной папки. GPKG не остаётся открытым при ошибке нормализации или прерывании чтения.
  • Выявленный при полном тесте NetworkTimeout: 3 секунды на операцию MongoDB оказались недостаточны для архива cases. CLI использует 30 секунд; backend без дополнительных переменных сохраняет прежние тайм-ауты. Права не изменены.
  • Подтверждённые вставки учитываются после каждого пакета. При сбое status=failed, counts_are_confirmed_only=true: незавершённый пакет не объявляется успешным. Повтор insert-only дозаполняет недостающие ID, не удаляя прежние документы.
  • Добавлены import_geojson.py/import_gpkg.py, сохранён единый import_data.py. Для плоских связанных записей автоматически создаются Location/Foci, geometry приводится существующим строгим конвертером модели без ложного unsupported type.
  • Предупреждение дополнительного Excel-листа агрегируется по листу; строки архивируются все, количество показано в archive_only_rows. Это не потеря данных.
