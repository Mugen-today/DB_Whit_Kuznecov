# Обновление редакций 6/7 и старой структуры

Эта инструкция относится к существующей базе. Для новой базы используйте README. Приложенный архив содержит исправленный код, а не копию ваших данных.

1. Сохраните рабочий .env отдельно. Остановите все писатели, включая старые Download/Upload и внешние клиенты. Создайте согласованную резервную копию mongodump и проверьте её восстановление в отдельную базу. Автоматическое резервное копирование не настроено.
2. Остановите прежний стек без удаления volumes. Не выполняйте down -v. Не запускайте два mongod с одним томом.
3. Распакуйте новую редакцию в чистую папку или обновите через Git. Копирование поверх старой папки может оставить удалённые model.v6.json/storage_schema.json. Перенесите сохранённый .env, а не старые скрипты.
4. Через docker volume ls проверьте точные имена данных. Настройки STORAGE_DATA_VOLUME и STORAGE_CONFIG_VOLUME должны указывать старые тома. Не выполняйте volumes, если пытаетесь восстановить доступ к существующей базе с неизвестным именем тома.
5. В PowerShell выполните:

```powershell
py scripts/manage.py configure
py scripts/manage.py config --connections
py scripts/manage.py migrate-plan
```

На Linux/macOS замените py на python3. Configure добавляет только отсутствующие новые секреты. Неверные или пустые существующие значения не исправляет. Root-пароль должен совпадать с реальной базой. Manage.py использует .env; временные переменные терминала теперь не переопределяют параметры проекта.

6. После успешного плана и с остановленными писателями:

```powershell
py scripts/manage.py migrate
py scripts/manage.py up --connections --local-api
py scripts/manage.py verify
py scripts/manage.py network-test
```

Миграция переименовывает Pdtient → Patient, Setlement → Settlement, Municipality.setlement → settlement, Building.courpus → corpus, Patient.medical_record.сhronic_diseases → chronic_diseases (кириллическая первая буква). ObjectId, ссылки и значения сохраняются; cases.raw остаётся первичным материалом. Затем применяются актуальные валидаторы, индексы и роли. Поле _owner_id добавлено в схему, но старым документам владелец не назначается автоматически.

Если одновременно существуют старое/новое имя коллекции или оба поля в одном документе, выполнение останавливается до записи. Даже пустая целевая коллекция автоматически не удаляется. Разрешите конфликт после сопоставления данных. Миграция повторяема, но не является единой транзакцией; после прерывания возможен частичный результат. Проверка количества записей не заменяет backup.

Migrate-plan останавливает backend и запускает Storage: это не полностью пассивная команда. Сам скрипт работает без записи, но на пустом томе Docker entrypoint выполнит начальную инициализацию. Поэтому сначала проверьте тома.

Если имена уже исправлены, повторная миграция применит текущие валидаторы/роли и не должна переименовывать данные повторно. Если verify проходит, для обычных следующих запусков миграция не нужна.

Смена .env не меняет существующий пароль MongoDB. Provision создаёт отсутствующих пользователей и обновляет назначения, но сохраняет пароли. При потере пароля восстановите его из сохранённой конфигурации либо проведите явную административную смену пароля и согласованно обновите .env. Не удаляйте ради этого рабочую базу.
