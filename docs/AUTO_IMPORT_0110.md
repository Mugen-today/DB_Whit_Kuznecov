# Автоматический консольный импорт — 0.11.0

> Обновление 0.11.1: команды Excel/JSON и --dry-run/--apply описаны в [README](../README.md#import-version-20). Прежний плоский Excel — scripts/import_excel_records.py.


После обычного запуска проекта укажите только путь. MongoDB должна быть готова;
импорт не запускается при init/up. Из корня проекта в PowerShell:

```powershell
py scripts/import_data.py "D:\Sources\test_datasetA_ispr_1.xlsx" > import-A.jsonl
py scripts/import_data.py "D:\Sources\testB_normalized_final.json" > import-B.jsonl
py scripts/import_data.py "D:\Sources\data.geojson" > import-geo.jsonl
py scripts/import_data.py "D:\Sources\data.gpkg" > import-gpkg.jsonl
```

Linux/macOS: python3 вместо py. Путь может содержать пробелы/кириллицу. Команда
собирает одноразовый импортёр, монтирует только выбранный файл read-only и запускает
общий backend-модуль auto_import. Прогресс сборки идёт в stderr, полный JSONL-отчёт
— в stdout. Старые команды import_excel сохранены для совместимости; у новой
команды нет выбора режима и ручной карты полей. Самих исходников в проекте нет.

## Распознаваемые структуры

- XLSX образца A: имя листа — коллекция, первая строка — поля. Дополнительные
  исходные листы архивируются в cases и явно отмечаются как не нормализованные.
- JSON образца final B: массив объектов с разделами Patient, Therapy, Instances,
  Location, Foci, Address_Refs и справочниками. JSON-массив читается постепенно.
- GeoJSON FeatureCollection: properties содержит такие же разделы либо поля
  Collection.field; geometry должна быть 2D Point EPSG:4326. FeatureCollection
  сейчас загружается в память целиком — ограничения числа записей нет, но нужен RAM.
- GPKG: таблицы с именами коллекций/полями модели либо таблица связанных записей
  с полями Collection.field. Также распознаются однозначные имена passport, age,
  diagnosis, Longitude/Latitude; registered/started/event_date соответствуют
  Patient.reg_date/Therapy.date_start/Instances.date. Геометрию Point и CRS
  преобразует существующий backend-адаптер. Неизвестная CRS останавливает импорт.

Произвольные имена вроде name/type без контекста коллекции не угадываются.
Нераспознанные данные архивируются в cases с предупреждением, а не исчезают.
GeoJSON/GPKG не проверялись на реальных образцах пользователя: такие образцы
не предоставлены; проверены генерируемые тестовые структуры выше.

## ID, типы и связи

Используется MongoDB `_id` типа ObjectId; дублирующее поле id не добавляется.
Корректные 24-символьные исходные ID сохраняются с преобразованием BSON-типа.
Числовые/другие ключи Excel нормализуются прежним алгоритмом namespace
`test-dataset-a`, чтобы ссылки совпадали с предыдущим импортом. Для остальных
сгенерированных ключей используется SHA256 источника, коллекция и позиция строки.
Повтор неизменённого файла сохраняет те же ID. Изменённый источник без явных ID
может создать другие документы — это не поиск одинаковых людей по атрибутам.

Исправляются Bouilding/Setlement/Settelment, courpus, treatment_procedure,
_id_instance/id_instance и Foci.instances. Ссылки приводятся к направлениям
model.json; Location.address.geodata связывается с Geodata, Foci.location — с
Location, Foci.id_instance — с Instances.instance. Геометрия сохраняется как
GeoJSON Point, Longitude/Latitude согласованы. ISO-даты становятся BSON Date,
числовые/логические поля и массивы преобразуются по модели.

## Историческая неполнота и ограничения модели

Это административный исторический импорт с техническими полномочиями хоста,
а не ослабление API создания новых записей. В предоставленных образцах есть
NULL passport/age и неоднозначные справочники. Отсутствующие значения не
выдумываются: документ сохраняет допустимую моделью хранения неполноту,
предупреждение попадает в отчёт. Строгие правила интерактивного API не изменены.

Неизвестные поля и исходные ошибочные значения сохраняются в cases. Значение,
которое нельзя привести к типу модели, исключается из нормализованного документа
с явной ошибкой поля в отчёте. Неразрешённая ссылка исключается с ошибкой; фиктивная
целевая сущность не создаётся. Исходная ссылка остаётся в cases.

В B один ID улицы может ссылаться на несколько зданий, а модель допускает только
одну ссылку Street.building. Аналогичные конфликты бывают в других справочниках.
Такую ссылку нельзя переносить выбором «последнего» значения: она исключается,
помечается внутренним _ambiguous_links, все исходные связи архивируются. Полностью
выразить такую связь без изменения модели на один-ко-многим невозможно.
Конфликт остальных атрибутов одного ID — критическая ошибка до начала записи.

## Запись и отчёт

Вся адаптация и проверка выполняются в служебном SQLite до записи. Затем документы
вставляются пакетами по 250, существующие ID не обновляются. Поэтому сохраняются
прежние пользовательские правки. В конце cases получает архив исходных строк.
Если запись прервана, ранее подтверждённые пакеты остаются; повтор той же команды
дозаполняет отсутствующие ID без дубликатов. Общей транзакции файла нет. Внешние
ссылки проверяются перед записью, но конкурентное удаление документов внешними
инструментами после проверки этим историческим путём не блокируется.

Отчёт содержит stage, collection, row, field, reason, severity; последняя строка
содержит summary: SHA256, исходные строки, число нормализованных документов,
вставленные документы и количество сообщений. Счётчик issues включает предупреждения,
а не только ошибки. Все сообщения выводятся без ограничения preview в 100 строк.
При критическом сбое процесс возвращает ненулевой код. Для прямого Python-вызова
доступно `python -m app.modules.auto_import FILE --report REPORT.jsonl` из backend
с настроенным окружением MongoDB. Не направляйте stdout в сам исходный файл.

Датасеты/отчёты могут содержать персональные данные; храните их вне Git. Существующие
.env, MongoDB volumes и том импорта при обновлении сохраняются. Обновите backend
и ZIP плагина вместе; ожидаемая версия сессии 0.11.0. Предыдущие руководства 0.10
описывают прежние команды и оптимизацию; эта инструкция задаёт новый консольный путь.
